# Лабораторна робота №4: Біометрична автентифікація
## Мета роботи
Додати до застосунку біометричну автентифікацію (Touch ID / Face ID / Fingerprint). Застосунок має перевіряти наявність датчика, пропонувати біометрію як альтернативу паролю та коректно обробляти всі можливі стан успіх, відмову, недоступність датчика.

## Керування біометрією (`InternalBiometricManager`)
Логіка роботи з датчиком повністю інкапсульована у класі `InternalBiometricManager`. Для доступу до апаратної частини у файл `AndroidManifest.xml` було додано дозвіл `<uses-permission android:name="android.permission.USE_BIOMETRIC" />`.

### 1. Перевірка доступності (`checkAvailability`)
Метод звертається до системи та повертає зрозумілий для UI статус наявності датчика:
* `Sensor Ready` - датчик готовий до роботи.
* `No Hardware` - пристрій не має сканера.
* `Hardware Unavailable` / `Not Enrolled` - сканер є, але не налаштований користувачем.

### 2. Керування станами (`BiometricStatus`)
Усі процеси автентифікації є асинхронними, тому стан запиту зберігається централізовано у `StateFlow<BiometricStatus>`. Використовуються такі стани:
* `Idle` - очікування.
* `Authenticating` - викликано системне вікно сканування.
* `Success` - відбиток підтверджено.
* `Failed` - помилка розпізнавання або скасування користувачем.
* `Unavailable` - датчик недоступний.

### 3. Збереження налаштувань (`SecurityPreferences`)
Вибір користувача щодо використання біометрії (увімкнено/вимкнено) зберігається у `SharedPreferences` (режим `MODE_PRIVATE`). Це гарантує, що налаштування безпеки зберігаються між перезапусками програми. Значення зчитується одразу при старті у `MainViewModel`.

## Інтеграція з UI та Нові екрани

Біометричний захист було інтегровано у **три різні сценарії** взаємодії:

### Сценарій 1: Екран блокування при старті (`LockScreen`)
Якщо користувач увімкнув біометрію в налаштуваннях і пристрій підтримує її (`isSensorReady == true`), `MainActivity` автоматично блокує контент програми. Замість головного меню відображається екран `LockScreen` (Рис.1.).
* **Поведінка:** Застосунок викликає `BiometricPrompt`. Тільки після отримання статусу `Success` змінна `isAppContentLocked` змінюється на `false`, і користувач отримує доступ до навігації.
* **Резервний вхід:** Передбачена кнопка "Аварійний вхід" для обходу блокування на випадок тестування або відмови датчика.

### Сценарій 2: Екран налаштувань безпеки (`SecurityCombinedScreen`)
Об'єднаний екран керування (доступний через нижню навігацію) (Рис.2.), де користувач може:
* Побачити поточний стан датчика (наприклад, "Sensor Ready").
* Увімкнути або вимкнути запит біометрії за допомогою `Switch` (тумблера).
* Зміни миттєво записуються у `SecurityPreferences`.

### Сценарій 3: Підтвердження критичної дії (`ConfirmDeleteScreen`)
Захист небезпечних операцій (Рис.3.). При спробі видалити квест з бази даних замість звичайного діалогу "Ви впевнені?" відкривається спеціальний екран. Система вимагає відсканувати палець. Метод `viewModel.deleteCampaign(id)` викликається **тільки** якщо колбек біометрії повернув `onAuthenticationSucceeded`.

## Автоматизоване тестування (`BiometricLogicTests.kt`)

Для перевірки логіки безпеки написано **14 Unit-тестів**. Оскільки апаратний датчик неможливо прямо протестувати в Unit-тестах, використано патерн **Mocking** (через бібліотеку MockK).

**Що перевіряють тести:**
1. **Ізоляція станів:** Перевірка правильної ініціалізації (`Idle`) та переходів у стани `Success`, `Failed` та `Authenticating`.
2. **Збереження даних:** Перевірка того, що клас `SecurityPreferences` коректно викликає методи збереження (`setBiometricEnabled`) та читання.
3. **Обробка відсутності датчика:** Перевірка логіки застосунку у випадку статусу `Unavailable` (заглушка для емуляторів без налаштованого профілю).
4. **Валідація текстових даних:** Перевірка наявності тексту опису (`reason`) для системного діалогу біометрії, що є обов'язковою вимогою API Android.
