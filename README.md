# Лабораторна робота №2: Локальне сховище та взаємодія з сервером
## Мета роботи
Підключити локальне сховище та визначити стратегію взаємодії з сервером: застосунок по винен вміти зберігати дані на пристрої та мати чітку відповідь на питання - що відбува ється без інтернету.

## Локальне сховище (Room)
Для збереження даних між перезапусками застосунку була обрана структурована БД - **Room**. Це дозволяє ефективно керувати зв'язками, забезпечує типізацію на етапі компіляції та підтримує реактивні потоки даних (Flow).

### 1. Сутність бази даних (`CampaignEntity`)
Модель даних адаптовано для роботи з БД. Додано поле `syncStatus`, яке відповідає за відстеження стану синхронізації (вимога стратегії Offline-first).
* `@PrimaryKey val campaignId: String`
* `val syncStatus: String` (наприклад: "synced", "pending")
* Інші поля: `title`, `difficultyLevel`, `isCompleted`, `releaseDateTimestamp`

### 2. Операції доступу до даних (`CampaignDao`)
Реалізовано всі 4 обов'язкові операції:
1. **Зберегти (Create/Update):** `insertCampaigns(campaigns: List<CampaignEntity>)` з політикою `OnConflictStrategy.REPLACE`.
2. **Прочитати список (Read All):** `observeAllCampaigns(): Flow<List<CampaignEntity>>`. Використання `Flow` гарантує, що будь-які зміни в БД автоматично тригерують оновлення UI.
3. **Прочитати один об'єкт (Read One):** `getCampaignById(id: String): CampaignEntity?`.
4. **Видалити (Delete):** `deleteCampaignById(id: String)`.

## Мережева взаємодія та API-контракт

### Стратегія комунікації: Offline-first
Застосунок завжди працює з локальною базою даних (`Room`). Локальне сховище виступає як єдине джерело правди (Single Source of Truth).
* **Читання:** UI завжди читає дані лише з БД.
* **Синхронізація:** При натисканні кнопки "Синхронізувати" (`refreshFromServer`) або при появі мережі застосунок робить запит до API і записує нові дані в БД. Після збереження в БД інтерфейс оновлюється автоматично завдяки `Flow`.
* **Робота без інтернету:** Застосунок повністю функціональний.

### API-контракт (REST)
Для імітації серверної частини створено клас `QuestApiService`, який містить мок-дані та штучну затримку (`delay(1500)`), імітуючи мережевий HTTP-запит. У майбутньому цей шар буде замінено на Retrofit.

| Метод | Ендпоінт | Опис | Тіло запиту / Параметри | Відповідь (Response) |
| :--- | :--- | :--- | :--- | :--- |
| **GET** | `/api/v1/campaigns` | Отримання списку всіх доступних квестів-кампаній. | Немає | `200 OK`, JSON масив об'єктів `Campaign` |
| **GET** | `/api/v1/campaigns/{id}` | Отримання детальної інформації про конкретну кампанію. | Шлях: `id` (String) | `200 OK`, JSON об'єкт `Campaign` |
| **DELETE**| `/api/v1/campaigns/{id}` | Видалення кампанії на сервері (імітація). | Шлях: `id` (String) | `204 No Content` |

## Repository Pattern (`QuestRepository`)

Для інкапсуляції логіки роботи з даними реалізовано патерн "Репозиторій". Клас `QuestRepository` приймає дві залежності:
1. `campaignDao: CampaignDao` (Локальна БД)
2. `apiService: QuestApiService` (Мережевий шар)

**Основний сценарій синхронізації:**
Метод `syncCampaigns()` виконує наступне:
1. Запитує дані з сервера: `apiService.fetchCampaignsFromServer()`.
2. Отримані дані відразу зберігаються в локальну БД: `campaignDao.insertCampaigns(remoteData)`.

## Зв'язок з UI
Зв'язок бази даних з інтерфейсом реалізовано через `MainViewModel`. Інтерфейс **ніколи не чекає** відповіді від сервера безпосередньо.

1. **Миттєве оновлення списку:**
   В `ViewModel` змінна `campaignsList` підписана на БД через `repository.observeAllCampaigns().stateIn(...)`. Коли викликається видалення (`deleteCampaign`) або синхронізація (`refreshFromServer`), Room автоматично пушить новий список, а Jetpack Compose перемальовує екран без потреби писати логіку ручного оновлення масивів в UI.
2. **Збереження стану:**
   Після перезапуску застосунку, оскільки дані зберігаються у фізичному файлі SQLite на пристрої, екран списку одразу завантажує збережені кампанії.
