# Лабораторна робота №3: WebSocket та Автоматизоване тестування
## Мета роботи
Додати до застосунку real-time канал через WebSocket та покрити ключову логіку автоматизованими тестами. Застосунок повинен реагувати на події від сервера без перезавантаження екрана, а критичні частини коду перевірятись автоматично, не вручну.
## WebSocket-з'єднання (`SocketManager`)
Для керування постійним з'єднанням з сервером реалізовано окремий клас `SocketManager`, який інкапсулює роботу з бібліотекою `OkHttp`. 

### Керування станами
Стан з'єднання строго типізований за допомогою `enum class SocketState` і зберігається у реактивному потоці `StateFlow`. Підтримуються наступні переходи:
`Disconnected` ➔ `Connecting` ➔ `Connected` ➔ `Reconnecting` ➔ `Disconnected`.

### Основні методи:
* `connect(url)` — ініціює HTTP-запит для підняття WebSocket-сесії. Якщо з'єднання вже встановлено, повторний виклик ігнорується.
* `disconnect()` — коректно закриває з'єднання з кодом `1000 (Normal closure)` та переводить стан у `Disconnected`.
* `send(message)` — відправляє текстове повідомлення на сервер.
* Читання повідомлень реалізовано через перевизначення методу `onMessage` інтерфейсу `WebSocketListener`, який транслює отриманий текст у реактивний потік `messages`.

### Автоматичне перепідключення (Retry Logic)
При обриві з'єднання (виклик `onFailure`) спрацьовує метод `handleFailure()`. Він перевіряє лічильник спроб. Якщо спроб менше встановленого ліміту (`maxRetries = 1`), стан змінюється на `Reconnecting`, і через 3 секунди (`delay(3000)`) застосунок автоматично намагається відновити зв'язок.

## Real-time оновлення UI та Нові екрани
Згідно з вимогами, до застосунку додано 2 нові екрани, які інтегровані в існуючу систему нижньої навігації (`NavigationBar`).

### 1. Екран налаштувань (`SettingsScreen`)
Цей екран демонструє роботу WebSocket у реальному часі без жодного ручного оновлення (pull-to-refresh) (Рис.1.). 
* **Статус з'єднання:** Інтерфейс підписаний на `socketStatus`. Колір індикатора динамічно змінюється (зелений для `Connected`, червоний для помилок).
* **Жива стрічка подій:** `MainViewModel` імітує отримання серверних push-сповіщень. Кожні 5 секунд, за умови активного з'єднання, генерується нова подія. `SettingsScreen` підписаний на потік `serverNotifications` і миттєво виводить нове повідомлення на екран.


### 2. Екран лідерів (`LeaderboardScreen`)
Додатковий екран, який відображає рейтинг гравців та їхній досвід. У майбутньому цей екран також буде отримувати дані через WebSocket для "живого" оновлення таблиці рекордів (Рис.2.).

## Автоматизоване тестування (`LogicTests.kt`)

Для гарантії надійності архітектури Data Layer (репозиторій, БД, API) написано **15 Unit-тестів**, які перевіряють критичну логіку без запуску емулятора. Для ізоляції залежностей використано бібліотеку **MockK**.

### Що саме протестовано (Ключові сценарії):
| Категорія | Перевірка |
| :--- | :--- |
| **Делегування (Repository ➔ DAO)** | Перевірено, що методи репозиторію (`deleteCampaign`, `getCampaignById`) коректно викликають відповідні методи локальної бази даних (`coVerify`). |
| **Синхронізація (Offline-first)** | Тест `test sync saves to database` гарантує, що дані, успішно завантажені з API, передаються в метод `insertCampaigns` для збереження. |
| **Обробка помилок мережі** | Тест `test fetch from server error handling` симулює падіння мережі (`throws Exception`) і перевіряє, що програма не крашиться, а запис у БД просто не відбувається (викликів `insert` рівно 0). |
| **Мапінг та перетворення даних** | Перевірено правильність зчитування полів сутностей БД (`title`, `syncStatus`, `difficultyLevel`) для уникнення помилок серіалізації. |
| **Реактивність (Flow)** | Тест `test dao observation returns data` перевіряє, що репозиторій успішно транслює потоки даних (`flowOf`) з DAO до ViewModel. |

Запуск тестів відбувається миттєво, що дозволяє безпечно рефакторити код у майбутньому.
